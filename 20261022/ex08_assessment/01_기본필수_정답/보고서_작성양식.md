# Multi Agent 실행 로그 EDA · 강사용 예시 보고서

## 질문과 데이터
어느 역할의 실행이 느리고 어느 측정의 관측이 부족한가? PPT 16~17쪽의 합성 로그 13행을 사용했다. 한 행은 Agent 한 번의 실행이다. 실제 서비스 벤치마크/요금이 아니고 latency 합을 워크플로 지연이라고 볼 수 없다.

## 정제 정책
모든 열이 동일한 R03 한 행만 제외해12행을 보존했다. ID만 같고 값이 다른 기록은 임의 선택하지 않고 중단한다. 공백/대소문자를 정리했다. latency/tokens는 숫자로 변환하고 변환불가·음수·무한대를 결측으로 두었다. 0은 유효한 관측이다. error3행도 전체분모에 남겼다. R11의 invalid날짜는 NaT이며900ms는 삭제하지 않았다. data는 읽기 전용 입력으로 취급하고 검증된 결과만 out에 게시했다.

## 근거 3개
| 관찰 | 수치와 분모 | 근거 | 한계 |
|---|---|---|---|
| researcher의 평균이 가장 높다 | 566.67ms, 유효3/전체4 | summary.json, latency_by_agent.png | 작업 난이도가 같다는 정보가 없어 성능 원인을 확정할 수 없다 |
| latency관측이 일부 없다 | R08·R09·R10, 결측 3/전체12 | quality.json | 결측0대체는 평균을 왜곡한다 |
| 느린 관측을 확인할 필요가 있다 | 900ms1건; 전체평균317.78ms/중앙값250ms, 유효 9건 | latency_hist.png | 작은 표본의 꼬리만으로 오류나 서비스전체 분포를 단정할 수 없다 |

성공률은 planner3/4=75%, researcher2/4=50%, writer4/4=100%이다. 유효 측정9건의 평균과 전체12건의 성공률 분모는 다르다.

## 확장 분석 시 참고
역할메타 결합은12행을 유지한다. 가상 비용0.436은 토큰이 측정된11건의 부분합이다. 날짜미상1건을 분리하면10-21과10-22의 평균은245ms로 같으나 유효/전체는6/6과2/5이다. 기본필수에서는 이 확장 출력이 없어도 공통 채점기준을 충족할 수 있다.

## 한계와 개선안
관측이 적고 역할·작업·상태가 섞여 있다. 동일 작업조건과 관측기간을 맞추고, 결측 이유를 추가 수집한 뒤 비교한다. 확장 데이터를 사용했다면 이 고정 예시 문장을 그대로 제출하지 말고 out/facts.json의 실제 수치로 갱신한다.

## 검증과 기여
이 문서는 강사용 해석 예시다. 코드 자동 실행은 검수 보고서에 기록했다. 실제 수강생의 기여·동료 리뷰·기관 제출·본인 Git 활동은 수행자가 별도로 적는다. 미실시 항목을 완료로 간주하지 않는다.
