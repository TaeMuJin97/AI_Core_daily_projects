# Multi Agent 실행 로그 EDA · 강사용 예시 보고서

## 1. 분석 질문과 데이터
어느 역할의 실행이 느리고 어떤 측정의 관측이 부족한가? PPT 16~17쪽의 합성 로그 13행을 사용했다. 한 행은 Agent 한 번의 실행이다. 실제 서비스의 벤치마크나 요금 데이터는 아니다. 개별 latency의 합을 곧바로 전체 워크플로의 지연시간으로 해석할 수는 없다.

## 2. 정제 정책
모든 열이 같은 R03 한 행만 제외하여 12행을 보존했다. ID만 같고 값이 다른 기록은 임의로 선택하지 않고 중단한다. 역할·상태의 공백과 대소문자를 통일했다. latency와 tokens는 숫자로 변환하고 변환 불가·음수·무한대는 결측으로 두었다. 0은 유효한 관측이다.

실패 3행도 전체 분모에 남겼다. R11의 `invalid` 날짜는 NaT로 처리하되 900ms 측정은 삭제하지 않았다. `data`는 읽기 전용 입력으로 취급하며 검증된 결과만 `out`에 반영했다.

## 3. 근거 3개와 해석
| 관찰 | 수치와 분모 | 근거 파일 | 해석의 한계 |
|---|---|---|---|
| researcher의 평균이 가장 높다. | 566.67ms, 유효 3건 / 전체 4건 | `../out/summary.json`, `../out/charts/latency_by_agent.png` | 작업 난이도가 같다는 정보가 없어 원인을 확정할 수 없다. |
| latency 관측이 일부 없다. | R08·R09·R10, 결측 3건 / 전체 12건 | `../out/quality.json` | 결측을 0으로 대체하면 평균을 왜곡한다. |
| 느린 관측을 추가로 확인할 필요가 있다. | 900ms 1건, 전체 평균 317.78ms / 중앙값 250ms, 유효 9건 | `../out/charts/latency_hist.png` | 작은 표본의 꼬리만으로 오류나 서비스 전체 분포를 단정할 수 없다. |

성공률은 planner 3/4=75%, researcher 2/4=50%, writer 4/4=100%이다. 평균은 latency가 측정된 9건을, 성공률은 전체 12건을 기준으로 계산한다.

## 4. 확장 분석 참고
역할 메타데이터 결합 전후로 12행을 유지한다. 가상 비용 0.436은 토큰이 측정된 11건의 부분합이다. 날짜 미상 1건을 따로 표시하면 10월 21일과 22일의 평균은 245ms로 같지만 유효 수 / 전체 수는 각각 6/6과 2/5이다. 기본필수에서 확장 출력이 없어도 공통 채점 기준을 충족할 수 있다.

## 5. 한계와 개선안
관측이 적고 역할·작업·상태가 혼재되어 있다. 동일한 작업 조건과 관측 기간을 맞추고 결측 이유를 추가 수집한 뒤 비교해야 한다. 확장 입력을 사용했다면 이 예시의 고정 수치를 그대로 제출하지 않고 `out/facts.json`의 실제 결과로 갱신한다.

## 6. 검증과 개인 기여
이 문서는 강사용 해석 예시이다. 코드 실행 결과는 검수 보고서에 기록했다. 실제 수강생의 기여·동료 리뷰·교육기관 제출·본인 Git 활동은 수행자가 별도로 기록한다. 미실시 항목을 완료로 간주하지 않는다.
