# 📐 Day 23 Architecture Notes: Embedding · pgvector · Retriever 전체 지도 및 파이프라인 설계

**핵심 아키텍처 요약**: Day 23에서는 Embedding, pgvector, Retriever(검색 결과 평가 포함) 파이프라인을 구축하며, 기존에 구축한 **11/10-11 기반(FastAPI, PostgreSQL)**과 **11/16-17 기반(Context 구성, Prompt 조립, LLM Client, 출력 검사)**을 그대로 유지한 채 의미 기반 검색 계층(Semantic Retrieval Layer)을 결합합니다.

---

## 🗺️ 1. 전체 지도 (End-to-End Architecture) 한눈에 보기

전체 시스템은 크게 **① 기존 백엔드/DB 기반**, **② 오늘 구축한 Semantic Search 파이프라인(`Embedding → pgvector → Retriever → 검색 결과 평가`)**, **③ 기존 Context · LLM 응답 생성 및 검증 계층**, **④ 후속 RAG · Agent 확장 영역**의 4개 축으로 동작합니다.

```text
[사용자 (질문·요청)]
       │ (질문) / ▲ (응답)
       ▼          │
[11/10 FastAPI (요청·응답)] ───(조회)───► [11/11 PostgreSQL (원문·Metadata)]
       │                                         │ (고정)
       │                                         ▼
       │                                  [16·17일 유지: 지식 101~103 (고정된 원문 ID)]
       │                                         │ (선택한 자료)
       ▼ (질문)                                   ▼
[11/16 Context 구성 (검색·자료 선택)] ◄───(검색한 근거)───┐
       │                                                 │
       │  ┌────── [오늘의 검색 · 이후 RAG에서 호출] ───────┴──────────────────────┐
       │  │  1. [오늘·입력 벡터] Embedding (query · passage / 384차원 정규화)     │
       │  │         │ (벡터)                                                    │
       │  │         ▼                                                           │
       │  │  2. [오늘·PostgreSQL 확장] pgvector (벡터 저장·검색 / <=>, HNSW)     │
       │  │         │ (검색)                                                    │
       │  │         ▼                                                           │
       │  │  3. [오늘·검색 반환] Retriever (Top-k · 원문 후보 직렬화)             │
       │  │         │ (검색한 근거)                                              │
       │  │         ▼                                                           │
       │  │  4. [오늘·정성평가] 검색 결과 평가 (원문 관련성·이유 / 근거 충분성)    │
       │  └─────────────────────────────────────────────────────────────────────┘
       │
       ▼ (문맥)
[11/16 Prompt 조립 (지시·근거·계약)] ◄──(요청 조건)── [검색 결과 평가]
       │ (입력)                     ◄──(같은 입력·형식 수정 1회)──┐
       ▼                                                        │ (형식 오류)
[11/17 LLM Client (응답 생성 호출)] ───(응답)───► [11/16~17 출력 검사 (Schema·ID·근거)]
       │ (통신 오류)                                     │ (자동 통과)
       ▼                                                 ▼
[11/17 실패·중단 (구분·기록)]                      [11/16 근거 검토 (원문 사실 확인)]
                                                         │ (검토 결과 반환)
                                                         ▼
                                                  [FastAPI ──► 사용자 응답]
```

## 📖 2. 전체 지도 절차별 상세 해설 (Step-by-Step Narrative Guide)

위 아키텍처 다이어그램이 실제로 어떻게 움직이는지, 사용자의 질문이 들어와서 최종 답변으로 나가기까지의 전체 여정을 5단계의 흐름으로 풀어서 설명합니다.

### 1단계: 사용자 요청의 유입과 원본 데이터의 보존 (FastAPI → PostgreSQL)
모든 흐름은 **사용자**가 자연어로 질문(예: *"서버는 어디에서 실행하나요?"* 또는 *"실습 파일은 얼마나 보관하나요?"*)을 던지면서 시작됩니다.

1. **API 관문 (`11/10 · 기존 기반: FastAPI`)**:
   - 사용자의 요청을 가장 먼저 받는 것은 FastAPI 서버입니다. FastAPI는 사용자의 입력을 검증하고, 내부 파이프라인을 거쳐 완성된 최종 응답을 다시 사용자에게 돌려주는 입출구 역할을 맡습니다.
2. **원본 저장소 (`11/11 · 기존 DB: PostgreSQL` 및 `16·17일 유지: 지식 101~103`)**:
   - 지식의 원문(`title`, `content`)과 메타데이터(`id`, `category`, `source_version`)는 PostgreSQL 데이터베이스가 단일 진실 공급원(SSOT)으로 관리합니다. 지난 11/16~17일 실습에서는 `101`, `102`, `103`번 지식을 고정된 원문으로 가져와 Context에 직접 넣었습니다.
3. **데이터 확장과 안전한 격리**:
   - 실무에서는 수백, 수천 개의 문서 중 질문에 맞는 것만 골라내야 합니다. 이를 위해 오늘 실습에서는 기존 `101~103`번의 ID와 원문 내용을 절대 수정하거나 덮어쓰지 않은 채 `104~109`번 문서를 추가해 총 9개의 지식 세트를 만들었습니다.
   - 특히 기존 운영 테이블(`knowledge`)을 삭제(`DROP`)하거나 변형하지 않고 검색 전용 테이블(`day23_search_docs`)을 별도로 생성함으로써, 기존 백엔드 기반을 안전하게 유지하면서 검색 기능을 확장했습니다.

### 2단계: 의미를 숫자로 바꾸고 가장 가까운 후보 찾기 (Embedding → pgvector → Retriever)
단순 키워드 일치(`LIKE '%서버%'`)만으로는 표현이 조금만 달라져도 문서를 찾지 못합니다. 따라서 오늘 구축한 세 가지 핵심 모듈이 순서대로 작동하여 **의미 기반 검색(Semantic Search)**을 수행합니다.

1. **문장과 질문을 384차원 벡터로 변환 (`오늘 · 입력 벡터: Embedding` — 실습 `01`, `02`, `03`)**:
   - 다국어 임베딩 모델인 `intfloat/multilingual-e5-small`을 사용하여 텍스트를 384개의 실수로 이루어진 벡터로 변환합니다.
   - 이때 E5 모델의 핵심 계약인 **비대칭 검색(Asymmetric Search) 접두어 분리**를 적용합니다. DB에 저장할 지식 문서 앞에는 `"passage: "`를 붙이고(`"passage: {title} {content}"`), 사용자가 입력한 검색 질문 앞에는 `"query: "`를 붙여야(`"query: {question}"`) 모델이 '찾을 대상'과 '질문'의 역할을 구분해 같은 의미 공간에 정확히 배치합니다.
   - 또한 모든 벡터의 길이를 1로 맞추는 L2 정규화(`normalize_embeddings=True`)를 수행하여 내적(Dot Product)과 코사인 유사도(Cosine Similarity)가 일치하도록 만들고, 모든 값이 0인 영벡터(Zero-vector)나 `NaN`은 수학적으로 방향을 계산할 수 없으므로 코드 단계에서 `ValueError`로 즉시 차단합니다.

2. **DB 내부에서의 벡터 저장과 고속 거리 계산 (`오늘 · PostgreSQL 확장: pgvector` — 실습 `04`, `05`, `06`)**:
   - PostgreSQL 18.6 서버에 `vector` 확장(`v0.8.7`)을 활성화하고, Python(`psycopg`) 연결마다 `register_vector(conn)`를 등록해 파이썬 배열과 DB의 `vector(384)` 컬럼을 양방향으로 매핑합니다.
   - 파이썬에서 만든 384차원 벡터를 원문, 메타데이터(`source_version`, `embedding_model`)와 함께 `day23_search_docs` 테이블 한 행(Row)에 묶어서 원자적으로 저장(`INSERT ... ON CONFLICT DO UPDATE`)합니다.
   - 질문 벡터가 들어오면 `pgvector`의 코사인 거리 연산자(`<=>`)를 사용해 거리를 계산합니다. 유사도(Similarity)는 클수록 가깝지만 **거리(`Cosine Distance = 1 - Cosine Similarity`)는 0에 가까울수록(작을수록) 유사한 문서**이므로, 반드시 오름차순(`ORDER BY embedding <=> %s ASC LIMIT k`)으로 정렬합니다.
   - 이때 다른 임베딩 모델이 만든 벡터와 섞여 엉뚱한 거리가 계산되지 않도록 `WHERE embedding_model = %s` 조건을 필수로 걸어줍니다. 또한 대규모 데이터를 대비해 `USING hnsw (embedding vector_cosine_ops)` 근사 인덱스를 생성하는 법을 익히되, 현재처럼 데이터가 9건뿐인 작은 테이블에서는 DB 옵티마이저가 인덱스를 타는 것보다 테이블 블록 하나를 한 번에 읽는 순차 스캔(`Seq Scan`)을 선택하는 것이 비용상 훨씬 유리하고 정상적인 동작임을 `EXPLAIN (ANALYZE, BUFFERS)` 실측으로 확인했습니다.

3. **원문 후보 묶음 반환 (`오늘 · 검색 반환: Retriever` — 실습 `08`)**:
   - `Retriever`는 위 과정을 하나로 캡슐화한 검색 모듈입니다. 먼저 질문이 빈 문자열이나 공백이 아닌지 외부 API 연결 없이도 동작하는 순수 함수(`validate_question`)로 가장 앞단에서 검사합니다.
   - 만약 DB 연결이 끊어지는 등 시스템 장애가 발생했을 때 이를 빈 리스트(`[]`)로 조용히 덮어버리면, 상위 시스템이 '조건에 맞는 문서가 없는 정상 상태(`empty`)'로 착각하게 됩니다. 따라서 Retriever는 DB 예외를 숨기지 않고 그대로 전달하며, 검색된 상위 `k`개 문서의 6가지 핵심 정보(`id`, `title`, `content`, `category`, `source_version`, `distance`)를 어떠한 요약이나 변조도 없이 그대로 다음 단계에 전달합니다.

### 3단계: 검색된 문서가 진짜 정답 근거인지 따져보기 (오늘 · 정성평가: 검색 결과 평가 — 실습 `07`)
전체 지도 중앙에서 **`Retriever` 바로 위에 위치한 `검색 결과 평가(원문 관련성·이유)`** 박스는 오늘 수업에서 가장 강조하는 핵심 검증 단계입니다.

1. **"가장 가까운 문서 1등"이 곧 "정답 근거"는 아니다**:
   - SQL의 `LIMIT 3`은 DB에 있는 문서 중 상대적으로 덜 먼 3개를 무조건 뽑아올 뿐입니다. 따라서 `distance` 숫자가 작다고 해서 그를 '정답 확률(%)'로 해석하거나 자동으로 답변 완료(`answered`) 상태를 부여하면 안 됩니다.
2. **`retention` 케이스가 보여주는 대표적인 근거 부족 사례**:
   - 실제로 *"실습 파일은 얼마나 보관하나요?"*(`retention`)라고 질문하면, 어휘가 비슷한 `101`번 문서(*"실습 파일은 workspace 폴더에 보관합니다."*)가 코사인 거리 1순위로 검색됩니다.
   - 하지만 원문을 직접 읽어보면 보관 **장소(`workspace`)**만 적혀 있을 뿐, 질문이 묻는 핵심인 보관 **기간(얼마나)**에 대한 정보는 전혀 없습니다. 즉, 벡터 검색(Retrieval) 자체는 작동했지만 질문에 답할 근거로는 불충분한 **'부분 관련(근거 부족)'** 상태인 것입니다.
3. **평가 결과의 반영 및 상태 분리**:
   - 이처럼 검색 결과를 수동 기준표(`관련` / `부분 관련` / `무관`) 및 원문과 대조해 점검하고, ① 후보가 없는 정상 빈 결과(`empty`), ② DB 연결/쿼리 장애(`error`), ③ 후보는 반환됐으나 원문 근거가 부족한 상태를 엄격히 구분해 기록합니다. 근거가 부족할 때는 억지로 답변을 지어내지 않도록 다음 단계인 `Prompt 조립`에 요청 조건(근거 부족 시 답변 보류 규칙 등)을 전달하고, 근본적으로는 누락된 정책 데이터를 추가 적재하도록 유도합니다.

### 4단계: 기존 Context · LLM 파이프라인을 통한 안전한 응답 생성 (11/16~17 재사용)
검색과 평가를 통과한 원문 후보들은 우리가 지난 이틀간(Day 21~22) 구축해 둔 검증된 LLM 파이프라인으로 합류합니다.

1. **문맥 구성 및 프롬프트 조립 (`11/16 Context 구성` → `11/16 Prompt 조립`)**:
   - 고정 지식(`101~103`) 또는 `Retriever`가 찾아온 Top-k 원문 후보를 토큰 예산(`margin` 확보) 안에서 선택하여 문맥(Context)을 구성합니다.
   - 여기에 시스템 지시사항, 검색 결과 평가에서 넘어온 요청 조건, 그리고 출력 형식 계약(JSON Schema)을 결합해 최종 프롬프트를 안전하게 조립합니다.
2. **LLM 호출과 통신 장애 분리 (`11/17 LLM Client` → `11/17 실패·중단`)**:
   - 완성된 프롬프트를 `LLM Client`에 전달해 응답 생성을 호출합니다. 만약 이 과정에서 API 키 오류(401), 권한 오류(403), 한도 초과(429)나 네트워크 타임아웃 같은 **통신 오류**가 발생하면 즉시 `실패·중단` 모듈로 분기하여 원인을 구분하고 기록합니다.
3. **출력 형식 검사와 1회 제한 재시도 (`11/16~17 출력 검사` → `같은 입력 · 형식 수정 1회`)**:
   - LLM이 응답을 반환하면 Pydantic 스키마를 통해 필수 필드, 참조한 문서 `ID`, 근거 포함 여부를 검사합니다.
   - 만약 JSON 형식이 깨졌거나 스키마 계약에 어긋나는 **형식 오류**가 발견되면, 무제한 재시도로 비용과 시간을 낭비하지 않고 **같은 입력에 대해 형식 수정 1회(`bounded_retry`)** 루프를 통해 `Prompt 조립` 단계로 되돌려 교정을 시도합니다.
4. **최종 사실 확인 및 반환 (`11/16 근거 검토` → `FastAPI` → `사용자`)**:
   - 출력 형식 검사를 자동 통과한 응답이라도 실제 원문 사실과 일치하는지 마지막으로 `근거 검토`를 거친 뒤, 검증 로그를 남기고 FastAPI를 통해 사용자에게 최종 응답을 반환합니다.

### 5단계: 향후 확장 방향 (Chunk 단위 RAG 및 AI Agent · Tool API)
전체 지도의 점선 영역은 오늘 만든 `Embedding → pgvector → Retriever` 구조가 앞으로 어떻게 확장되는지를 보여줍니다.

1. **Chunk 기반 실전 RAG 연결 (`오늘의 검색 · 이후 RAG에서 호출`)**:
   - 문서가 길어지면 문서 전체를 하나의 벡터로 만들지 않고 의미 단위 조각(`Chunk`)으로 쪼개어 `pgvector`에 저장합니다. 이후 Day 25 RAG 파이프라인에서는 오늘 만든 `Retriever`를 그대로 호출해 질문과 가장 관련 있는 조각들을 실시간으로 가져와 `Context 구성`에 주입하게 됩니다.
2. **Agent 제어와 외부 도구 실행 (`이후 · Agent 제어` → `권한 확인 → Tool API`)**:
   - 단순 질의응답을 넘어 AI가 직접 행동(예: DB 상태 변경, 외부 시스템 조회, 도구 실행)을 제안해야 할 때는 `Agent 제어` 계층이 상태와 도구 호출을 관리합니다.
   - 이때 AI가 임의로 위험한 도구를 실행하지 못하도록 반드시 **별도의 보호 계층인 `권한 확인(승인된 도구 실행)`** 절차를 거친 뒤에만 `Tool API`를 실행하며, 실행된 도구 결과는 다시 상단 파이프라인으로 전달되어 최종 응답에 반영됩니다.

## 🔍 4. 핵심 정성평가 회고 (`07_relevance` · `outputs/exercise_07.json` 검토 요약)

- **검토 배경**: `pgvector`의 `ORDER BY embedding <=> %s ASC LIMIT 3` 쿼리가 반환한 상위 3개 후보의 코사인 거리(`distance`) 수치와 실제 질문에 답할 수 있는 원문 근거 충분성을 대조함.
- **검토 결과**:
  1. 현재 생성되는 `distance` 값만으로는 두 벡터가 질문의 정답을 담고 있을 만큼 유사하다는 절대적 근거가 될 수 없다(`LIMIT 3`에 의해 DB 내 상대적 상위 3건이 무조건 반환되기 때문).
  2. 특히 `retention`(*"실습 파일은 얼마나 보관하나요?"*) 케이스에서는 `101`번 문서(*"실습 파일은 workspace 폴더에 보관합니다."*)가 1순위로 검색되나, 원문에 보관 **위치**만 있을 뿐 보관 **기간**에 대한 정보가 누락되어 있어(`부분 관련`) 답변 근거로 사용할 수 없다.
- **아키텍처 조치 방향**:
  - 검색된 후보를 곧바로 답변 완료(`answered`)로 처리하지 않고, 원문 대조 시 근거가 불충분하면 `insufficient_context`(근거 부족)로 분기하여 환각(Hallucination)을 차단해야 한다.
  - 근본적인 해결을 위해 실습 파일의 보관 주기 및 삭제 정책이 명시된 **추가 지식 데이터를 DB에 적재(Ingest)하는 것을 고려해야 한다**.
